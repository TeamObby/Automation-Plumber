**Add:**

**Not run:**

### B. Calls: one log, Kevin's names on top
- **`screener_log` stays the only call log anything writes** (Kevin's Major Tasks #5). n8n writes it through
  `screener_log_upsert`, and Log Retry replays any failed write.
- **`calls` is a read-only view** with Kevin's column names:
  - `caller = coalesce(<screener_user_id → name>, 'Topu')` *(decided: in the view, not stored; nothing on the live
    table changes, and it can be corrected later)*;
  - `outcome = coalesce(screener_outcome, No Answer / Voicemail / Wrong Number from the WAVV event)`;
  - `ai_mismatch = not match`;
  - leaves out `graduated` rows, and machine-answered `call` rows that have no mark (so a voicemail counts once).
- **`shop_call_state`** takes the list side from `shops.status` (loader-owned: new / held / queued / called_before)
  and the call side from each shop's latest `screener_log` row (via `ghl_contact_id`):
  - result stage → state; Owner Verified or graduated → "with Kevin";
  - `max(attempt_no)` = attempts; `min(event_at)` = first dial.
  - Nothing call-related is stored in `shops`, so it has no second writer.
- **Kevin's six call fields plus Background** (`shop_id`, `number_dialed`, `how_he_answered`, `voicemail_greeting`,
  `first_name`, `best_time`, `background`) go into `screener_log` in the day-1 PR. The order matters: add the
  columns → recreate `screener_log_upsert` to include them (it lists columns explicitly) → change `log_call_row.js`
  **and** `log_attempt_row.js` (voicemails never pass the Compare Step).
- **The same PR hardens the upsert:** an undecided write (`result_stage` null) never replaces a decided row. Without
  it, a mark the Compare Step doesn't know overwrites the previous call's settled row with nulls; all three planners
  confirmed this. It covers every caller.

### C. No second system writing to GHL
- Kevin's `ghl-call` and `ai-check` are not deployed.
- The live n8n screener already:
  - moves stages and counts attempts;
  - runs a blind AI check on every call (Classify reads only the transcript);
  - tags `screen-mismatch` in real time.
- A second writer would double-count. Kevin's `log_call` also marks "owner confirmed" from Topu's pick alone, and has
  no dedupe.
- Because `calls` is a view, a later attempt to deploy either one fails loudly.
- Task 9 (next number) comes later, inside the n8n Attempt Counter.

### H. Where code runs, and how SQL gets applied
- **Repo `waterline-pipeline`** (private, Kevin as Owner). *Deferred 2026-09-26:* the database went in directly (SQL in
  this repo's `supabase/`); the repo is created when Tausif's connector or the batch loader needs it.
  - Kevin's code as commit 1;
  - all Supabase SQL, as `supabase/migrations/<version>_<name>.sql`, including the 5 live migrations under their
    exact versions;
  - loaders, batch files, Actions.
- **This repo:** the n8n screener stays in Automation-Plumber; its `supabase/*.sql` become pointers.
- **Python runs in GitHub Actions:** `workflow_dispatch` with a `--dry-run` default, and a `concurrency: loader` group
  so only one run at a time. Each run posts its counts to the PR or Slack as the receipt.
  - CI on PRs gets no secrets.
  - The service key lives in a GitHub **Environment** `production`, limited to `main`, with Mohimenul as required
    reviewer. It is a **separate** secret key from n8n's, so it can be revoked on its own.
  - Week 1: a `loader` Postgres role with no DELETE grant and no access to `screener_log`.
- **Migrations:**
  1. rehearse with `execute_sql` running `begin; <migration>; <asserts>; rollback;` (anon has no privilege on any new
     object; every view has `security_invoker`);
  2. then `apply_migration` of the unchanged file, with Mohimenul's OK.
  - No automatic `db push` on merge.
- **The CA load upsert is non-downgrading:** it updates list facts only, never lowers `status`, and fills
  `dial_number` / `ghl_contact_id` only when empty. CI runs it twice.
